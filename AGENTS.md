# Serato web library

Local browser for the Serato DJ Pro library. `server.py` uses the Python standard library. `desktop.py` opens that page in a native window and shuts the server down when the window closes. Optional sharing uses `sentry-sdk` and `posthog`, and stays off without a key and without consent. Python has no linter. The page uses ESLint. Tests use `unittest` and Vitest.

## Run

```bash
python3 server.py
```

Serves `http://127.0.0.1:8765`. A missing library still serves the page so setup can explain the next step. On macOS the usual library file is `~/Library/Application Support/Serato/Library/master.sqlite`. On Windows that file is `%LOCALAPPDATA%\Serato\Library\master.sqlite`. Stop the server with Ctrl-C.

The desktop app uses a local virtualenv, because Homebrew Python will not take a system-wide install:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python desktop.py
```

It binds `127.0.0.1` on a free port and opens a window titled crateCraft. Close the window to quit. A second launch focuses that window. On Windows, use `.venv\Scripts\python` in place of `.venv/bin/python`. On macOS, also install `requirements-macos.txt` so WKWebView can load. On Linux, install WebKitGTK (GTK 3 and WebKit2) or Qt WebKit. `.venv/` stays untracked. `CRATECRAFT_NO_WINDOW=1` or `--no-window` skips the window.

## Tests

```bash
python3 -m pip install -r requirements.txt
python3 -m unittest discover -s tests -t . -v
```

The suite imports `sentry-sdk` and `posthog`. It builds a temporary database. It does not open the live Serato library. Settings and logs for the run stay in a temporary directory.

The page tests, including the setup wizard, need Node 22 or newer:

```bash
npm ci
npm test
npm run typecheck
npm run build
npm run storybook
```

`npm run storybook` serves isolated React components at `http://127.0.0.1:6006`. Vite is the Storybook builder. The page still bundles with esbuild. Stories live in `src/stories/`, mirrored as `*.stories.tsx` under `components/`, `pages/`, or `containers/`. Context islands map Controls args through `src/lib/storybook/args.ts` into fixture providers. They do not mount the live `app/providers.tsx` stores. A push to `main` that changes those stories, `.storybook/`, or the page CSS publishes them at `https://mookiejones.github.io/crateCraft/storybook/`. `@storybook/addon-mcp` exposes MCP at `http://127.0.0.1:6006/mcp` while that process is running. `.grok/config.toml` registers it as `storybook`. When editing a component that has a story, use those MCP tools for docs and props.

The commands to paste into a pull request are the full list under [After a change](#after-a-change).

## Layout

The page uses a 200px navigation drawer and a 56px mini rail. Mini is forced at viewport widths of 980px or less. The AppBar player is a deck when the window is wider than 980px (160px SWF1 detail, overview, 22px pads, Play · title · time). Mini width keeps the compact strip. Cue pads in the AppBar jump; detail pads stay a list. `layout.drawer_open` remembers the last toggle. The Crates room shares tree, list, and detail so Title / Artist / BPM stay readable; a saved list width cannot hide the tree or the detail. Search sits above crate actions. New, Rename, and Delete stay on one row; extras sit under More. The Data Grid owns horizontal scrolling and visible keyboard focus. Crates puts a checkbox column first; checking two or more rows opens a field editor bar above the list. MUI shares the page font and existing colorways.

- `drive_check.py` reads a portable drive's `_Serato_` crates and reports tracks that are not on that drive, tracks that cannot be found, Smart Crates, and FAT32-unsafe names. `python3 drive_check.py DRIVE` prints the report. `GET /api/drive-check` returns the same JSON. It does not write to the drive. Organize files shows Check drive on a removable Serato root. **Check drive** under Gig shows the same report: the person picks a connected drive that has a `_Serato_` folder. An unmounted drive is named and is not treated as a missing file. **Copy smart crates** and **Restore smart crates** on Check drive write each smart crate's rules and its current tracks into that drive's `_Serato_/SmartCrates` folder. Restore is a preview, then a write while Serato is quit. A stick snapshot is saved before an existing drive crate is replaced. A stick whose crates belong to another library, or to no remembered library, is left as it was until confirm. Confirm saves that snapshot, then writes. The remembered library sits in `stick-exports.json` beside settings. The snapshot sits in `stick-snapshots` in that same folder, not inside `_Serato_`. **Review stick cues** lists cues that are on the stick and not in the library and writes nothing. **Import empty pads** copies those cues into empty pads and does not replace a cue the library already has. POST `/api/stick-cues` is preview or apply. An unplugged stick stays not connected.
- `rekordbox.py` writes a Rekordbox `DJ_PLAYLISTS` file and a loss report. `python3 rekordbox.py -o rekordbox.xml` prints the report. **Export**, **Import**, and **Rekordbox** show on Crates. **Rekordbox** opens a dialog with **Memory cues**, **Hot loops**, and the key notation, shows the report, and downloads the XML after confirm. **Hot loops** starts off and is remembered with Memory cues and the key notation in `settings.json`. The help line reads Uses a free hot-cue pad. Subcrates become nested playlist folders. Hot cues, loops, and the beatgrid are read with the Markers2 and BeatGrid parsers in `tags.py`. MP3 cue times are shifted from the LAME/Xing header, not by one amount for every file. Device Library Plus and OneLibrary are not written. Emoji and non-Latin crate names are kept, and the loss report names the ones a player may not display. Cues at the same millisecond are kept once. Hot cues stop at eight (A–H). Memory cues stop at 32, and the ones left out are named. The export still finishes. A beatgrid marker with under half a beat before the next marker or the end of the track is written one beat earlier when that time is still inside the track. Otherwise the loss report names it. The report is read-only until the download is confirmed.
- `export_pdb.py` parses one synthetic `export.pdb`-style page. It does not write a USB database, Device Library Plus, or OneLibrary, and the XML export does not call it. A page count uses a 13-bit field, so more than 255 rows stay visible. A truncated device-name row is regenerated as `USB`, zero-padded to 40 bytes, and named in the report. The damaged row is not copied.
- `gig_check.py` is a read-only pre-gig check. `python3 gig_check.py` prints a ready score and a Holding it back list. It opens the database through `library.read_conn` (copy then `mode=ro`) and audio with `rb`. It reads saved snapshots through `snapshots.SnapshotStore(..., recover=False)` and compares each snapshot's database copy and saved frames with the library now. `gig_snapshots.py` holds that comparison. With no snapshots the report says `No snapshots yet`. `volumes.py` names the drive a stored path lives on and whether it is plugged in, so a track on an unplugged drive is unavailable, not missing. `GET /api/library` and `GET /api/track` use that same split: Serato's missing flag on an unplugged drive becomes `offline` (with `offline_drive`), not `missing`. The Missing view lists only connected-drive missing files. Relink does not match offline tracks. `relink.py` suggests where missing tracks went, read-only: same name and size, same name, or same size and type, plus whole-folder moves. `python3 relink.py ROOT...` prints the plan, and `GET /api/relink?space=` searches the present music roots. Optional `root=` is an extra folder after a drive swap. The Missing view reviews matches and `POST /api/files` with `action: relink` rewrites the stored paths through the journal; audio is not moved.
- `snapshots.py` stores content-addressed, hash-checked snapshots of the database, per-drive `_Serato_` crates (including `database V2`), and Serato frames inside audio files. Frame bytes are read and written by `snapshot_frames.py`. `Export Backups` and `Lexicon` are never read or restored, including a Windows name with a trailing dot, a trailing space, or an alternate data stream. `POST /api/snapshots` with `action: prune` and `confirm` true holds that snapshot directory in the crateCraft trash beside settings for 7 days after remaining complete copies stay at `min_copies` (default 2). Unplugged or untrusted volumes, and a hash-failed snapshot, do not count. It refuses while Serato DJ is running and does not write the Serato library. Restore from that trash puts the directory back. A timed purge deletes it only after the window, and cancel stops that purge. Duplicate audio that this app removes goes to the same trash. Purge refuses a file another DJ app still uses, and a delete that would drop below the verified-copy minimum. Restore saves a snapshot first, writes a journal before the first replace, can be previewed without writing, and refuses while Serato DJ is running or while the Serato version is unknown or Protect Library is on or unread. Lucid beatgrid storage is not parsed. It then registers any restored `.crate` or `.scrate` the database has not heard of, through the same write guards as a crate edit and without a second snapshot while the restore journal is open, so Serato 4 and 5 do not delete those files on launch. Registration is skipped when the snapshot has no master database, when `master.sqlite` is missing, or when the database has no Serato Library space. In that last case the plan warns that Serato may remove those crate files, and the restore still finishes. A crate whose snapshot copy cannot be read is reported as skipped and is not registered. An unfinished restore is rolled back when the store opens. After the files are replaced, restore checks them again. When no crate was registered, the database files are compared by byte hash. When crates were registered, row counts are compared: the snapshot's rows plus exactly those crates. The read copies the database and its WAL and opens the copy read-only, so the live file, `-wal`, and `-shm` stay unchanged. Indexes, triggers, views, and `PRAGMA integrity_check` must match, and in the `serato` table only the revision may change. Skipped crate files are left out of the file check. A mismatch puts the pre-restore snapshot back. The restore journal is removed only after that rollback's hash check passes. A failed rollback stays in the operation log and is not reported as a success. `SnapshotReader` exposes `list_snapshots` and `load`. `serato_web.completeness.is_complete` is the shared check for a finished snapshot or backup. `restore` calls `verify_legacy_backup` when `backup_status` is `legacy, unverified`, before the pre-restore snapshot. The first launch of a new crateCraft version takes an `app-upgrade` snapshot whose reason is `before update to` that version, before any library write, and only while Serato DJ is not running. A failed snapshot, including Serato still open, blocks writes and does not record the version. A missing library only records the version.
- `music_mirror.py` copies library audio to a user folder (#394). `python3 music_mirror.py DEST` prints the preview. `--copy`, `--restore`, `--crate`, and `--relink` write. Dest cannot be `_Serato_`, the Serato library, or a music folder. Copy is a byte copy so GEOB cues survive, with a size and hash check after each file. A dest file is skipped only when its size and hash match. A same-name file with a different size or hash is copied again. Restore skips a newer laptop file. **Make crate** saves tracks that exist only on this laptop. Relink reuses `POST /api/files` `action: relink`. `GET /api/music-mirror?dest=&space=` is read-only. `POST /api/music-mirror` with `action` `copy` writes dest audio and may run while Serato is open. `restore`, `crate`, and `relink` with `confirm` true write; crate and relink need Serato quit. The page is **Music files** on Backups (`src/components/MusicMirrorPanel.tsx`).

- `write_queue.py` queues crate and track edits while Gig Lock is on or Serato DJ is running (#393). Queued writes sit in `write-queue.json` beside `settings.json` and do not touch the library. `GET /api/write-queue` lists pending and undo. `POST /api/write-queue` with `action` `preview` is read-only; `apply` with `confirm` true writes through the existing crate, track, and file writers after Gig Lock is off and Serato is quit. A fingerprint mismatch keeps both: the live crate stays, and crateCraft's copy is a sibling named `from crateCraft, {day} {Mon} {HH:MM}`. Applied items stay undoable for 30 days. Undo takes a fresh snapshot and skips when Serato changed the row since apply. SQLite I/O errors and Protect Library / unknown version still 409. Undo restores that one preimage. **Queue crate** is under More. **Queue track** is on the track and on a history entry. **Batch** on Backups is `src/components/BatchPanel.tsx`.

Gig Lock still queues a tag spelling as `/api/tag-clusters`. `action: cancel` stops the worker before commit (`safe_write` rolls back); after commit it is a no-op. `action: undo` restores the before-write snapshot with no nested job. - `serato_logs.py` reads the newest session logs in `_Serato_/Logs` and does not write them. A `[Library]` line names `master.sqlite` or `database V2`. A backup suffix after that name is ignored. A Serato DJ version line, including `Product name: Serato DJ Pro, Version: 4.0.10 (4010213)` and `Version: 5.0.0 (5001251)`, names Serato 4 or Serato 5. `Surface Version: 4.1` is OpenGL, not Serato DJ. A missing or empty folder leaves the installed-app version in place. A log can only make the write gate stricter. - `smart_presets.py` evaluates DJ presets (harmonic neighbours of a key, BPM within a range, not played in N months, or a nested AND/OR of native leaves), each optionally scoped to one crate and its subcrates (part 1 of #26). ## After a change

1. Update `docs/architecture.md` when behavior, the API, the layout, or the run path changes.
2. Update `CLAUDE.md` and `AGENTS.md` together. They are copies of the same text. Update them when the run command or the layout summary changes.
3. Update `docs/github.md` when a workflow, a release check, or a GitHub setting changes.
4. Update `PRIVACY.md` and the README when sharing, local logs, or telemetry keys change.
5. A change a DJ can see also updates `docs/wiki/` and the user guide (`docs/index.md`, `docs/guide/`, `docs/quick-start.md`, `docs/first-install.md`). Use the `updating-user-docs` skill.
6. Tests. Every behavior change or bug fix ships with tests in the same PR: Python `unittest` under `tests/`, page code as Vitest `*.test.ts` in `src/tests/`. A bug fix needs a test that fails before the fix. Use only synthetic fixtures (`tests/fixtures/`), never a real `master.sqlite`, `root.sqlite`, or audio file.
7. Before opening a PR, run all checks locally and paste the results in the completion report:
   ```bash
   python3 -m pip install -r requirements.txt
   python3 -m unittest discover -s tests -t . -v
   npm ci
   npx tsc --noEmit
   npx tsc --noEmit -p e2e
   npx eslint src e2e
   npm test
   npx playwright install chromium
   npx playwright test -c e2e/playwright.config.ts
   npm run build
   ```
   Commit the rebuilt `static/app.js` and `static/wizard.js`.
8. Push to a branch and open a PR. Never push to `main`.
9. Write the [completion report](#completion-report) in the pull request body. When the work has an issue, post the same report as a final comment on that issue.

## Test bar

QA (Gatekeeper, account `mookiejones-qa`) blocks a PR whose tests do not meet this bar:

- Tests must fail if the logic is broken. QA may mutation-test; weak tests that pass anyway get blocked.
- Cover the edge cases that apply to the change: Windows and macOS paths, symlinks and unmounted drives, Serato 4 vs Serato 5 data, and an empty or missing library.
- Never write extra files inside the Serato folder.

## Merge rules

- `main` is protected. Changes go in only through a pull request.
- If a new push dismisses the `mookiejones-qa` approval, re-request review.
- These checks must pass:

  - `tests (ubuntu-latest, Python 3.14)`

  - `tests (macos-latest, Python 3.12)`
  - `frontend (ubuntu-latest)`
  - `frontend (windows-latest)`
  - `frontend (macos-latest)`

Only releases and tags (including pre-releases) need Charles's (@mookiejones) explicit OK.

## Completion report

Every agent (Claude, Cursor, and others) finishes each issue with a completion report. The report goes in the pull request body. When the work has an issue, the same report is the final comment on that issue. `CONTRIBUTING.md`, `.github/pull_request_template.md`, and [docs/github.md](docs/github.md) use this template.

Saying "done", without the issue link, the pull request link, the commit SHA, and the test output, does not count. Never claim work you did not push. The SHA is a commit on the remote branch, and each test line is a command you ran on that commit.

**What changed** is at most three bullets. **Proof** uses the exact commands in [After a change](#after-a-change). Each command that prints a pass count includes that count. Each other command includes pass or fail. Proof names the CI status of every check in [Merge rules](#merge-rules) and includes a screenshot when the change is visible in the page. A change with no page UI says there is no screenshot. **Next** says what is needed from Charles (@mookiejones) or QA (`mookiejones-qa`). Merge only when [Merge rules](#merge-rules) allow it.

- **Issue:** link
- **PR and commit:** link and SHA
- **What changed:** up to 3 bullets
- **Proof:** the exact test commands with their pass counts, CI status, and a screenshot for UI changes
- **Not done / risks:**
- **Next:** what is needed from Charles (@mookiejones) or QA (`mookiejones-qa`)
